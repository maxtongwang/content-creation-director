# 9 · 统一交付验收

**何时用**：**任何阶段产出之前**，全部过这一关。
这是所有分支的唯一出口。

---

## 四条硬标准

不满足就不交付，说明缺什么，回对应环节。

### 一、能直接使用

产出是**成品**，不是建议。

```
❌ 建议标题写得更有悬念一些
✅ 三个标题，可直接复制粘贴的那种

❌ 开头可以更抓人
✅ 「现在是早上七点半，我在……」——可以直接念出来的那句

❌ 注意分镜的节奏
✅ 12 个镜头的表格，每个带景别、cut_reason、时长
```

自查：**用户拿到之后，还需要自己做判断吗？** 需要 → 没做完。

### 二、符合事实

不编造用户没说过的：经历、数据、身份、观点、地点、人名。

```
不确定 → 问，或者留空标注 <待补>
绝不 → 自己填一个看起来合理的
```

**尤其危险的三类**：
- 具体数字（成交额、粉丝数、时长）
- 具体经历（"你之前做过 X"）
- 具体资质（证书、头衔、年限）

自查：**这份产出里的每个事实，都能在 profile 或用户原话里找到出处吗？**

### 三、满足制作限制

用户**今天真的做得出来**。

对照 `profile.production`：

- [ ] 拍得到吗？（地点、时间、人、道具是否可及）
- [ ] 拍得了吗？（能否出镜、设备够不够）
- [ ] 剪得了吗？（edit_mode 是 human 却给了纯 JSON？）
- [ ] 发得出去吗？（标题字数、平台规则、合规）
- [ ] 产能撑得住吗？（weekly_capacity）

自查：**列出的东西里，有没有一样是他做不到的？**

### 四、内部一致 ★ 2026-08-10 新增

**产出改动之后，被它推翻的旧内容当场删掉或改写 —— 不留横幅、不留 vN、不留孤儿引用。**

真实失效记录（同一个项目，一轮之内）：
文件 39 → 9 → 8；一份文件里的条目 140 → 256 → 216 → 202 → 196，累计弃用 166 条；
章节删 4 节并重排，产生 22 处死引用；同一个总数在不同段落出现过 5 个版本。
用户原话：**「skill 里面的引导和方法应该可以获得一致性的结果，而不是像我们现在这样经常要清理。」**

#### 根因：产出模式是追加式的

```
追加式   每轮加新结论 → 旧的等人发现才删 → 必然积垃圾
替换式   每轮结束时，被推翻的当场删或改 → 不积
```

**「先加上，回头再清理」不是效率，是把成本转移给下一轮。**

#### 三条机械规则

| # | 规则 | 为什么 |
|---|---|---|
| **1** | **一个事实只写一处**，别处写引用不写副本 | 副本必然与本体脱节 —— 改一处忘另一处是最高频的失效 |
| **2** | **能算出来的数字不要手写** | 「共 216 条」这类计数一旦手写，内容一变就过时。写「见 X」或当场重算 |
| **3** | **引用用锚点，不用章节号** | 章节会重排，锚点不会。`[看板](#kanban)` 不是「见第 2 节」 |

#### 交付前跑一遍（能脚本化就脚本化，别用眼睛）

```
□ 计数一致    文中所有「共 N 条」重新数一遍，对不上就改
□ 无死引用    每个内部链接 / 文件名 / 编号，目标还在吗
□ 无重复维护  同一张表 / 同一个判定，是不是存在两份
□ 无孤儿章节  有没有整节在讲已经删掉的东西（只加「已失效」横幅 = 没做完）
□ 版本号一致  文件头、变更日志、正文里的版本号是同一个
```

> ⚠️ **加「🔴 本节已失效」横幅是权宜，不是交付。**
> 横幅只在「这一轮来不及重写、下一轮一定重写」时用，并且要写清什么时候重写。
> **超过一轮还挂着横幅的章节，直接删。**

> 这一条是原则十三（给客观工具）用在**自己产出**上：
> 一致性不该靠回头审，该靠交付前跑一遍能跑的检查。

## 交付前的八项通检

无论哪个阶段，产出前都过一遍：

| 检查 | 不过关就回 |
|---|---|
| 命中 `forbidden_topics`？ | `1-account` |
| 与 `styles` 定义的风格一致？ | `8-styles` |
| 配额、节奏是否越界？ | `7-review` |
| 语气是否出现 `forbidden_phrases`？ | `2-ip` |
| 命中 `tone.表达标准.forbidden_sentences`？ | `2-ip` |
| **口播 / 标题 / 字幕里出现了 `_internal_*` 字段的内容？** | `5-script` |
| 本次是否有 `[编导]` 声明行及**对应的 view 调用**？ | 补做，重新走环节 |
| 涉及用户经历的内容，是否核对过 `profile.ip_analysis`？ | `2-ip` |

最后一条尤其重要：**内部原则是判断依据，不是可念的句子。**

自动剪辑最容易犯的错就是把总结句直接写进文案——
因为那些句子读起来最「点题」，看上去正好适合当标题或开场白。
一旦写进去，观众听到的就是本人在自我评价，效果与本意相反。

判断方法见 `2-ip.md` 第五节：这句话如果是别人说你，是不是在夸你？

**关于经历核对**：曾把用户的职业路径写成「住宅经纪转商业」，
实际是「先做投资人，从做经纪开始两边就都会」——**涉及本人经历不可推断，必须查 profile**。
顺序、因果、身份，错一个整条内容就废了。

## 交付格式

每次交付包含三段，缺一不可：

```
1. 产出本体      —— 文件 / 表格 / 清单
2. 为什么这么定  —— 关键决策的依据（一到三条，不要长篇）
3. 下一步        —— 明确指向哪个阶段，或明确说「可以开拍了」
```

**第 2 段不能省。**没有理由，用户会按自己习惯改，改完就偏离了。
**第 3 段不能模糊。**「你可以考虑一下」不是下一步。

---

## 不确定时的处理

拿不准就**标出来**，不要糊过去：

```yaml
<待补: 这条数据我没有，需要你确认>
<假设: 我按你能出镜处理的，如果不行说一声>
<可选: 这一镜有余力再拍，缺了也成立>
```

**标注比猜测好。**用户能一眼看到哪里需要他补，这本身也是交付质量的一部分。
