# 1d · 扫号（MCP 自动读取）

**何时用**：用户已有账号，**且**手上有对应平台的 MCP 工具。

**和 `1c-backfill` 的关系**：`1c` 是同一件事的人工版。
`1d` 只是把「让用户贴数据」换成「自己去读」，**判断逻辑完全一样**——
读完之后仍然走 `1c` 的四步反推和断层分析。

**工具清单**：`references/mcp-tools.md`

---

> ★★★ **了解用户这一环：疯狂追问，榨干为止。**停得太早是最大的失效模式 ——
> 一个真实项目里最要命的四条事实全在第 14 轮之后，而「上次为什么停」到第 16 轮才问出来。
> **追问顺序与停止信号见 [`1b-discover`](1b-discover.md)。**

## 一、先确认能读

| 平台    | 探测                  | 读不到时                              |
| ------- | --------------------- | ------------------------------------- |
| 小红书  | `check_login_status`  | 未登录 → 提示登录一次，或转 `1c` 人工 |
| YouTube | `channels_getChannel` | 无 key 或频道找不到 → 转 `1c`         |

**探测失败不要停。**说一句「这个平台我读不到，你贴一下」，然后继续。

---

## 二、读什么

按这个顺序，读到够用就停，不要把配额烧完。

### 小红书

```
get_my_profile          昵称、简介、粉丝数、笔记数
list_feeds / 主页笔记    近 20 条：标题、封面、互动数
get_feed_detail         挑数据最好的 3 条 + 最差的 3 条，读评论
search_feeds            用户主赛道关键词，看同赛道在推什么
```

### YouTube

```
channels_getChannel     频道基础数据
channels_listVideos     近 20 条：标题、时长、观看数
videos_getVideo         最好的 3 条 + 最差的 3 条
transcripts_getTranscript  挑 2 条拉字幕 —— 语言习惯最准的来源，且不耗配额
```

---

## 三、从读到的东西反推

**四步反推与 `1c-backfill` 完全一致**，这里只说数据能多给什么：

| 数据源       | 人工版拿不到 / 拿得费劲 | 自动读之后                              |
| ------------ | ----------------------- | --------------------------------------- |
| 近 20 条标题 | 用户凭印象说            | 可直接归类句式，算每类的实际表现        |
| 互动数据     | 靠截图，容易只挑好的    | 好的差的一起看，避免幸存者偏差          |
| 评论区       | 用户很少主动提          | **观众实际怎么称呼他**，最接近真实人设  |
| 字幕         | 几乎不可能人工给        | 口头禅、句长、结构习惯，可直接进 `tone` |
| 发布时间     | 记不清                  | 真实节奏，供 `automation` 层用          |

### 特别值得挖的两件事

**一、观众的称呼。**评论区里观众叫他什么，就是实际人设——
经常和他自己写的简介完全不同，这个差异就是断层报告的核心。

**二、字幕里的语言习惯。**把 2 条字幕拉出来，直接能看出：
常用句式、口头禅、平均句长、是否有 AI 腔。这些填进 `profile.tone` 比问出来的准得多。

---

## 四、分平台各扫各的

用户在多个平台有号，**分开扫、分开判断，不要合并**。

```
小红书数据好 + YouTube 差   →  不是他不行，是 YouTube 的封装没做
只有一个平台有号            →  另一个平台的适配从 3-topic 时再补
```

同一个账号在不同平台的表现差异，本身就是 `references/platform-playbook.md`
第五节要的诊断输入。

---

## 五、标注推断来源

反推出来的 profile **必须标注每个字段是怎么来的**：

```yaml
pillars:
  探店: { tier: A, source: inferred } # 从数据聚类推出来的
business:
  sells: <空> # 数据里读不出来，必须问
forbidden_topics: [] # 必须本人说，不能推
```

| 标记               | 含义                                     |
| ------------------ | ---------------------------------------- |
| `source: scanned`  | 直接读到的事实（昵称、简介、发布节奏）   |
| `source: inferred` | 从数据推断的（支柱、句式偏好、观众认知） |
| 留空               | 数据里读不出来，**必须问人**             |

**推断项要给用户确认一遍**，不要当成既定事实往下走。

---

## 六、读完之后只问三件

和 `1c-backfill` 一样，数据能答的都不要再问：

1. 靠什么赚钱 / 想靠什么赚钱？
2. 有什么是你不想做的？
3. 哪条内容你自己最满意但数据一般？

---

## 出口

产出与 `1c-backfill` 相同：

1. 反推的 `profile.yaml`（每个字段标注 `scanned` / `inferred` / 待确认）
2. 断层报告（说的 / 做的 / 观众认知）
3. **分平台的表现对比**（多平台时）
4. 建议的切入阶段
